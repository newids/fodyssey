# MVP Building — MVP 구축 규칙

## 제품 정의

[새 아이디어 확정 후 재작성 — 서비스 한 줄 정의와 핵심 사용자 루프를 기재한다] 화면·문안 설계는 항상 "이 MVP가 심사에서 증명해야 하는 한 가지"를 기준으로 판단한다.

**우선순위 원칙 (CLAUDE.md §1-1)**: MVP는 이 프로젝트의 주 산출물이 아니다 — 기존 교육 프로그램 연계·확산 전략을 시연하는 보조 수단이다. 범위는 전략 문서의 연계 시나리오를 보여주는 최소한으로 제한하고, MVP 확장 요청이 연계 전략과 무관하면 오케스트레이터에 되물어 우선순위를 확인한다.

## 기술 스택 (기본값)

- React 18 + Vite 5, 의존성 추가는 명확한 사유 없이 금지 (런타임 의존성은 react/react-dom만 유지)
- **완전 정적**: 런타임 LLM/서버 호출 없음. 동적으로 보여야 하는 문안·해설은 데이터셋 메타데이터를 클라이언트에서 프로파일별로 렌더링 — 발표 중 네트워크·API 장애로 데모가 죽지 않는 구조
- 상태: localStorage (프로파일, 진행도, 기록)
- 테스트: vitest (`npm test`), 로직은 `src/lib/`에 순수 함수로 분리해 테스트
- 배포 대상: [새 리포 배포 구성 후 기재] — 배포 경로 확정 시 vite.config.js의 base 경로를 함께 관리한다

## 예산·품질 기준

- JS 번들 80KB gzip 이내 (`npm run build` 출력으로 확인)
- 모바일 우선(375px 기준). 접근성 요구가 있는 타겟이면 큰글씨·고대비·단계별 문장 우선
- LaTeX/MathJax 금지, 모든 문안 한국어
- 종료 조건: `npm test` 전체 통과 + `npm run build` 성공. 둘 중 하나라도 실패한 채 완료 선언 금지

## 데이터 원칙

- 데이터셋: `mvp/data/` (스키마 설계 참고: `reference/mvp-patterns/data/scam_dataset_v0.1.json` — 시나리오·정답·단서·난이도 구조). 실사례를 쓸 때는 패턴만 추출해 전면 재작성 — 원문 전재 금지
- 가상 표기 원칙: 전화번호는 0000 계열, URL은 `*.example`만 사용, 실존 기관은 "OO기관" 식 가상 표기
- [새 아이디어 확정 후 데이터 구성 원칙(예: 정답/오답 비율, 난이도 분포)을 기재]

## 파일 구성 관례

- 화면 컴포넌트: `src/components/{Name}.jsx` (PascalCase)
- 로직·데이터 변환: `src/lib/{name}.js` — 컴포넌트에 비즈니스 로직을 넣지 않는다
- 스타일: `src/styles/global.css`의 CSS 커스텀 프로퍼티 토큰을 재사용 — 새 색·크기 하드코딩 금지

## 작업 절차

1. 기존 코드(`mvp/web/`의 화면 흐름, `src/lib/`)가 있으면 읽고 현재 루프를 파악한다; 없으면 `reference/mvp-patterns/web/`의 구조를 참고해 스캐폴딩한다
2. 전략 문서의 요구를 화면·로직 단위 작업 목록으로 분해한다
3. 로직부터: `src/lib/`에 순수 함수 + vitest 테스트 → 통과 확인 후 컴포넌트 연결
4. `npm test` + `npm run build` 통과 확인, 번들 크기 기록
5. `docs/idea/_workspace/07_mvp_notes.md`에 변경 요약 작성 (전략 항목 ↔ 구현 매핑, 테스트·빌드·번들 결과, 잔여 항목)
